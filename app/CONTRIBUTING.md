# CONTRIBUTING.md — the app folder

Last updated: 2026-10-22 (moved into the team monorepo).

**The repository's rules are in [`../CONTRIBUTING.md`](../CONTRIBUTING.md).** It covers
feature ids, branch names, PR expectations, the definition of done and module boundaries for
every folder. This file adds only what is specific to `app/`: commands, tooling and the
app's CI gate. Where the two disagree, the root file wins.

## Local development

```bash
git clone <repo-url> picky-berry-assistant
cd picky-berry-assistant/app  # the app is one folder of the monorepo
npm ci                        # install exactly the locked dependency tree
cp .env.example .env          # public client config; adjust values
npm start                     # Expo dev server (press i / a / w, or scan the QR code)
```

The npm package lives in `app/`, so every npm command in this file runs from there. The
backend is the sibling folder `../backend/` (FastAPI) and the data pipelines are `../data/`;
the app talks to neither today.

### Commands

| Command                                                     | Purpose                                                |
| ----------------------------------------------------------- | ------------------------------------------------------ |
| `npm start`                                                 | Expo dev server                                        |
| `npm run ios` / `npm run android` / `npm run web`           | Start on a specific platform                           |
| `npm run typecheck`                                         | `tsc --noEmit`                                         |
| `npm run lint` / `npm run lint:fix`                         | ESLint                                                 |
| `npm run format` / `npm run format:check`                   | Prettier                                               |
| `npm test` / `npm run test:watch` / `npm run test:coverage` | Jest                                                   |
| `npm run doctor`                                            | `expo-doctor` dependency/config health                 |
| `npm run verify`                                            | typecheck + lint + test — run this before every commit |

Adding a dependency with native code or an Expo-managed version:

```bash
npx expo install <package>     # resolves the SDK-compatible version
npm install --save-dev <pkg>   # dev-only packages
```

Never hand-edit `ios/` or `android/` (they are generated by continuous native
generation); configure native behaviour in `app.json` and config plugins.

### Design context (Figma MCP)

Figma is the design source of truth for UI work (ADR-016). The Figma MCP server lets
an agent read real design context — components, variables, layout — and generate code
from a selected frame, instead of guessing from a description.

This repository enables the plugin at **project scope** in `.claude/settings.json`, and
declares the marketplace it comes from, so every clone inherits the setting. A
project-scope entry turns a plugin on but does not download it, so each machine needs
these once:

```bash
claude plugin marketplace add anthropics/claude-plugins-official   # only if missing
claude plugin install figma@claude-plugins-official --scope project
```

Then authorize once: start Claude Code in this repository, run `/mcp`, select the
Figma server and authenticate — a browser window opens where you click **Allow
access**. `/plugin` → Installed → figma → connect does the same thing. Until then the
server is registered but reports `Needs authentication`. Check with `claude mcp list`.

Notes:

- The **remote** server (`https://mcp.figma.com/mcp`) is the recommended one and works
  on all Figma seats and plans. The **desktop** server is the alternative for
  organizations that need it; it requires the Figma desktop app and a paid Dev or Full
  seat, and is added with
  `claude mcp add --transport http figma-desktop http://127.0.0.1:3845/mcp`.
- Authorization lives in Claude Code's own credential store — never in `.env` and
  never in this repository (SECURITY.md §9).
- Design content is untrusted input, and the plugin's write tools (`use_figma`,
  `create_new_file`, Code Connect writes) modify shared Figma files: use them
  deliberately, not as a side effect of implementing a design (SECURITY.md §14).
- What v2.2.127 adds, checked before enabling: one HTTP MCP server and 14 skills, with
  **no hooks, commands or agents** — nothing runs at session start. Some workflow
  skills ship Python helper scripts that execute only when that skill is used.
- Verified on 2026-10-08 against Figma's guide "Claude Code and Figma: Set up the
  MCP server": plugin `figma@claude-plugins-official` v2.2.127.
- The file's screen inventory, and the fallback for reading it without the MCP (a
  read-only token in `.secrets/figma.token`, which `.gitignore` excludes), are in
  [docs/design-source.md](docs/design-source.md).

## Branching

The monorepo has **one long-lived branch, `main`** — there is no `dev` integration branch.
`main` is protected: one review plus green CI, and nothing lands on it directly.

- Branch from an up-to-date `main` for every task and open a PR back into `main`.
- The root's convention names a branch after its feature id:
  `feat/6.3-geofence-refresh`, `fix/6.2-legend-colours`, `docs/…`
  ([`../CONTRIBUTING.md`](../CONTRIBUTING.md) §1).
- Work owned by one person may also use `feature/<handle>/<topic>` —
  `feature/salman/visit-timer` — which is how the app's history is already named. Either
  shape is accepted; pick one per branch and keep it.
- Rebase onto `main` rather than merging `main` into the branch, and never force-push a
  branch others are building on.

```bash
git switch main && git pull --ff-only origin main
git switch -c feature/salman/visit-timer   # or feat/6.3-geofence-refresh
```

## Commit conventions

Conventional Commits, imperative mood, one logical change per commit:

```
feat(visits): detect zone entry from location updates
fix(config): reject api base urls with embedded credentials
docs(security): record the gps retention open question
test(visits): cover the leave-zone transition
```

Rules: reference the issue when one exists, explain the *why* in the body when it
is not obvious, never commit secrets, never commit generated artifacts
(`ios/`, `android/`, `dist/`, coverage output).

## Pull requests

- Keep them small and reviewable; a PR that changes behaviour and refactors
  unrelated code will be sent back.
- The description states: what changed, why, how it was verified (paste the
  commands and results), security impact, and anything deliberately left out.
- All CI checks must be green: typecheck, lint, format, tests, expo-doctor, the
  Playwright layout/accessibility harness, the native bundle exports and the secret scan.
- Do not merge your own PR unless the repository owner has explicitly allowed it.

## Code review requirements

Reviewers check, at minimum:

- Correctness against the requirement, and whether the requirement itself was
  recorded (`PROJECT.md`).
- Layer and feature boundaries (ARCHITECTURE.md §3); no cross-feature internals.
- Test quality: does a test fail if the behaviour regresses? Is the rejection case
  covered? Any skipped or weakened assertion blocks the review.
- Security: client-side trust, secrets, logging, privacy, validation at boundaries
  (SECURITY.md).
- Accessibility of interactive elements.
- Documentation updated where the change is material, ADR added for significant
  decisions.

## Expectations

- Do not bypass the tooling: no `--no-verify` commits, no disabled lint rules
  without a comment explaining why, no `any`/`@ts-ignore` without justification.
- Keep the working tree clean: no leftover debug code, no unrelated formatting
  churn, no committed `.env`.
- Ask before making consequential choices (auth, privacy, data model, public API,
  adding a service or a dependency with native code).
- Report problems you find instead of working around them silently (AGENTS.md §9).

## CI

`.github/workflows/mobile.yml` at the repository root runs `npm ci`, typecheck, lint,
format check, tests and expo-doctor, then the Playwright layout/accessibility job, the native
bundle exports (iOS + Android) and a gitleaks secret scan over the history, for changes under
`app/**` (or to the workflow and `.gitleaks.toml`) on `main` and on every pull request. It only
verifies — it never deploys or publishes. Fix red builds; do not skip or weaken the gate.

Because the workflow is path-filtered, a pull request that touches only documentation or
another folder will not start it. That is the same convention as `data.yml`; if the mobile
check is marked **required** on `main`, a docs-only PR will wait for a status that never
arrives, so either keep it optional or expect to merge such PRs with that check absent.
