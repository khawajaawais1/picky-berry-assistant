# Feature 6.7 – Reasoning and Explainable Push Alerts

**Lead:** Asmer (ontology + rules) · **Co-owners:** Awais (job + DB), Sabih (FCM infra), Hassan (picky-server schema)
**Sprint:** 3 (18 Nov – 1 Dec 2026) · **Status:** ✅ backend complete and deployed · FCM pending Firebase credential · app deep-link pending (Salman)

## In one paragraph
Every morning the backend scores every zone against the OWL ontology's ripeness rules and
sends the highest-scoring picks to each picker's phone as a push notification with a plain
English sentence — "Ripe Bilberry in zone 18 near Laajavuori — yield score 82, medium
confidence." Each alert names the rule and version that fired it, making every notification
auditable and the biology behind it legible. Users who haven't filtered by species receive
all four pilot species; those who chose a subset receive only their choices.

## Architecture

```
06:00 Helsinki (APScheduler cron)
        │
        ▼
_fetch_zone_rows(db)          zones JOIN zone_species (suitability ≥ 0.30)
        │
        ▼
_apply_scores(ZoneGrid, as_of) score_points() → {score, confidence, ripeness} per species
        │
        ▼
alerts_from_rule(ontology, rows, rule)   copy ontology graph → add_zone_rows → SPARQL query
        │                                rules: ripe_nearby.rq, ripe_soon.rq
        ▼
_write_run(db)         → alert_rules_log row (audit + observability)
_write_alerts(db)      → alerts rows (served by GET /api/v1/alerts)
        │
        ▼
push_alerts(db, alerts, fcm_app)
  ├── score ≥ 70 AND confidence ≠ "low"
  ├── is_quiet_hours() → skip if 21:00–07:00 Helsinki
  ├── user_alert_count_today() → skip if ≥ 2 today
  ├── zone_cooldown_active()  → skip if same zone × species within 3 days
  └── messaging.send_multicast(tokens, notification, data)
              │
              ▼
        push_log row (status: sent | failed)
```

## Hybrid AI pipeline: ML ↔ Ontology ↔ Infrastructure

Feature 6.7 is a **three-stage hybrid AI pipeline**. Each stage has one job and one job only.

```
┌─────────────────┐   ┌──────────────────┐   ┌─────────────────┐
│   berry_ml      │   │  ontology +      │   │   Postgres +    │
│   (ZoneGrid)    │   │  SPARQL rules    │   │   FCM           │
│                 │   │                  │   │                 │
│  "numbers"      │ → │  "which numbers  │ → │  "store + send  │
│                 │   │   deserve an     │   │   notification" │
│  score: 82      │   │   alert, worded  │   │                 │
│  ripeness: ripe │   │   in English"    │   │                 │
└─────────────────┘   └──────────────────┘   └─────────────────┘
      ML               Symbolic AI             Infrastructure
```

### Stage 1 — ML: `berry_ml.ZoneGrid.score_points(points, date)`

**File:** `ml/berry_ml/zones.py` · **Owner:** Remon · **Called from:** `backend/app/modules/reasoning/job.py::_apply_scores`

Not a trained neural network — a deterministic formula built from Finnish forestry data:
```
score = 100 × site_potential × ripeness × year_quality / 2 × 1.6
```

**Inputs:**
- `ml/models/zones/v2/zone_grid.csv` (6.4 MB) — 60×60 km grid of 256m × 256m cells around Jyväskylä, each cell knowing the share of every forest type (from Luke's MS-NFI 2023 maps)
- `RIPENING` dict in `zones.py` — phenology windows per species (DOY ranges at 62°N, shifted ~2 days later per degree north)

**Output per zone centroid:**
```python
{"bilberry":    {"score": 82, "confidence": "medium", "ripeness": "ripe"},
 "lingonberry": {"score": 71, "confidence": "medium", "ripeness": "ripe"},
 "cloudberry":  {"score": 0,  "confidence": "low",    "ripeness": "past"},
 "crowberry":   {"score": 45, "confidence": "low",    "ripeness": "ripening"}}
```

Takes ~4 seconds for all 4,865 zones once per daily run.

### Stage 2 — Symbolic AI: Ontology + SPARQL rules

**Files:** `ontology/bpa.ttl`, `ontology/species.ttl`, `ontology/rules/*.rq` · **Owner:** Asmer
**Loaded by:** `backend/app/modules/reasoning/graph.py::load_ontology`

The score alone is not an alert — it's just a number. The ontology + rules turn numbers into **"stories pickers can act on"**:

1. `add_zone_rows(graph, scored_rows)` adds RDF triples to a copy of the ontology:
   ```turtle
   zone:Ukonvuori-4-bilberry a bpa:SpeciesAssessment ;
       bpa:species bpa:Bilberry ;
       bpa:ripenessStage bpa:Ripe ;
       bpa:yieldScore 82 ;
       bpa:zoneSuitability 0.706 .
   ```

2. SPARQL rule `ripe_nearby.rq` runs against the combined graph and keeps only rows where `ripenessStage = bpa:Ripe AND suitability >= minHabitatSuitability`.

3. The `.rq` file header template becomes the push sentence:
   ```
   # sentence: Ripe {nameEn} in zone {zoneNumber} near {placeName} — yield score {yieldScore}, {confidence} confidence.
   ```
   → *"Ripe bilberry in zone Ukonvuori 4 — yield score 82, medium confidence."*

**Why ontology instead of hardcoded Python ifs:**
- Every alert traces back to `rule_id` + `rule_version` (explainability).
- Botanist edits `minHabitatSuitability` in `species.ttl` → no Python change, no redeploy.
- Adding a new rule = dropping a `.rq` file in `ontology/rules/`.
- Future hooks (LLM chat F1, Linked Data F3) consume the same ontology.

### Stage 3 — Infrastructure: Postgres + FCM

**Files:** `backend/app/modules/reasoning/job.py` (DB writes), `backend/app/modules/push/fcm.py` (FCM), `backend/app/modules/push/throttle.py` (guards)

Writes rows to `alerts` + `alert_rules_log`, then `push_alerts()` enforces the Layer-6 throttle guards and calls `messaging.send_multicast` for everyone subscribed to that species.

## Data model

### New tables (applied to Supabase 2026-11-22)

**`alerts`** — one row per zone × species per reasoning run.
Key columns: `run_id` (FK → alert_rules_log), `zone_id`, `species`, `rule_id`, `rule_version`,
`score`, `confidence`, `ripeness`, `suitability`, `sentence`, `computed_at`.
Indexes: `(zone_id, species, computed_at DESC)`, `(computed_at DESC)`, `(rule_id, run_id)`.

**`alert_rules_log`** — one row per rule execution (observability + audit).
Key columns: `rule_id`, `rule_version`, `zone_count`, `alert_count`, `status`, `error`, `duration_ms`, `run_at`.

**`push_log`** — one row per FCM send attempt (throttle state + audit).
Key columns: `user_id`, `alert_id`, `zone_id`, `species`, `fcm_token`, `status` (`sent`|`failed`), `sent_at`.
Partial indexes: `(user_id, sent_at DESC) WHERE status='sent'` and `(user_id, zone_id, species, sent_at DESC) WHERE status='sent'`.
RLS enabled on all three tables.

**`zone_features`** — daily ML input (zone static + weather + NDVI).
Built by `picky-data zone-features`; consumed by ZoneGrid and future XGBoost.

## Frontend integration (Salman)

The mobile app already registers FCM tokens via `POST /me/devices` on sign-in (built).
The remaining work is: **handle the notification tap and deep-link into the right zone card.**

### What arrives on the device

**Notification (what the OS shows):**
```
Title: Berry alert: Bilberry
Body:  Ripe bilberry in zone Ukonvuori 4 — yield score 82, medium confidence.
```

**Data payload (hidden fields the app reads on tap):**
```json
{
  "ruleId":     "ripe_nearby",
  "species":    "bilberry",
  "zoneId":     "082f0e54-03f4-5636-be4a-3f39d243a696",
  "score":      "82",
  "confidence": "medium"
}
```
All data values are strings (FCM data limitation). Convert `score` to int when needed.

### What the app should do on tap

1. **Parse `data.zoneId`** from the notification payload.
2. **Navigate** to the Discover screen's zone detail card for that `zoneId`.
3. (Optional) **Pre-select the species** (`data.species`) in the zone card header.
4. (Optional) **Highlight** the score/confidence in the UI as "incoming alert".

### How to test locally (without Firebase set up)

Trigger a reasoning run and inspect what `/api/v1/alerts` returns — the shape in the push
`data` field is a subset of each alert object:
```bash
curl -X POST "https://picky-backend-cd0u.onrender.com/api/v1/reasoning/run?as_of=2026-08-15"
sleep 10
curl https://picky-backend-cd0u.onrender.com/api/v1/alerts | jq '.[0]'
```
Take any `zoneId` from the response and manually deep-link to the zone card to verify the
navigation path works. When FCM is enabled later, the same `zoneId` arrives through the push.

### What the app should NOT do

- Do not re-query the backend for the alert on tap — the push already carries everything
  needed to open the right zone card. The `GET /api/v1/alerts` endpoint is for the alerts
  inbox screen, not for push handling.
- Do not filter or re-apply throttle rules on the device — the backend has already applied
  score ≥ 70, confidence ≠ low, quiet hours, rate limit and zone cooldown before sending.
- Do not store the notification data as a permanent record on the device — the inbox screen
  reads `/api/v1/alerts` for the authoritative list.

### Expo / FCM configuration checklist

- `expo-notifications` is installed and permissions handled on launch (built).
- `POST /me/devices` sends `{ fcm_token, platform }` on sign-in and on token refresh (built).
- Add a notification-received listener with `Notifications.addNotificationResponseReceivedListener`
  that reads `response.notification.request.content.data.zoneId` and calls the zone-navigation
  function from the Discover feature (**pending**).

## Risks and open questions

| Risk | Impact | Mitigation |
|------|--------|------------|
| Free Render tier spins down after 15 min inactivity | 06:00 cron may miss if service is sleeping | Upgrade to paid tier before launch, or add an external keep-alive ping |
| Firebase credential not yet set | FCM push disabled | Awais generates key from Firebase Console and adds `FIREBASE_CREDENTIAL_JSON` in Render dashboard |
| `ecologyVerified = false` for all species | Alerts disclose unverified ecology | Acceptable for v1; Asmer sources phenology data for v2 |
| Render Python 3.14 — `psycopg2` has no wheel | DB writes fail | Fixed: switched to `psycopg[binary]>=3.1` (psycopg3) |
| `::uuid` cast syntax breaks psycopg3 | `_write_alerts` SQL error | Fixed: replaced with `CAST(... AS uuid)` |
